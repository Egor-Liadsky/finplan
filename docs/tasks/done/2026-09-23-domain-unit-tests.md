## Задание

Покрыть модульными тестами на pytest доменное ядро в `tests/unit/domain/`.
Тесты проверяют правила документа, а не повторяют реализацию: ожидаемое
значение берётся из раздела документа, а не из кода.

Что покрыть обязательно:

- `Currency`: допустимый код ISO 4217 и `minor_unit`, отказ на недопустимых.
- `Money` по разделу 3.1: сложение и вычитание в одной валюте;
  `CurrencyMismatchError` при смешении валют; умножение на `Decimal` и `int`
  и отказ на `float`; деление возвращает `Decimal`; округление до
  `minor_unit` по `ROUND_HALF_UP` на граничных значениях (например,
  `Decimal("0.005")` → `0.01`, `Decimal("-0.005")` → `-0.01`,
  `Decimal("2.675")` → `2.68`); `Money.zero`; отказ принять `float` в
  конструкторе. Для законов арифметики — ассоциативности сложения, обратимости
  `a + b - b == a`, нуля как нейтрального элемента — использовать
  `hypothesis` (раздел 11.1).
- `Period`: полуинтервал `[from, to)` — левая граница входит, правая нет;
  отказ при `from >= to`; `for_day` и `for_month`, включая декабрь и
  високосный февраль.
- `Transaction` по разделам 3.3 и 4.2: положительный знак суммы; соответствие
  вида операции и вида категории; сторно — исходная операция переходит из
  `posted` в `reversed`, сторнирующая запись копирует исходную и создаётся
  сразу в статусе `reversed`; повторное сторно даёт `AlreadyReversedError`;
  сторно операции не в статусе `posted` отклоняется.
- `Category`: правило слагов `path` (`^[a-z][a-z0-9_]*$`) и ограничение
  глубины из раздела 3.3; `build_default_categories` строит 33 категории,
  27 расходных и 6 доходных, все с одним владельцем, все `path` уникальны,
  у каждой дочерней родитель есть в наборе и того же вида.
- `Account` и `User` — инварианты из раздела 3.3, каждый хотя бы одним
  положительным и одним отрицательным случаем.

Если тест обнаруживает расхождение кода с документом, код не чинить: тест
пометить `pytest.mark.xfail(strict=True, reason="...")` с описанием
расхождения и записать его в «Вопросы диспетчеру» с `file:line`.

## Результат исполнителя

**Сделано.** В `tests/unit/domain/` (уровень «Модульные» из 11.1, чистый
Python, без IO) добавлено семь файлов, каждый закрывает один пункт списка
«Что покрыть обязательно»:

- `test_currency.py` — допустимый код ISO 4217 (три заглавные латинские
  буквы) и диапазон `minor_unit` 0–4, отказ на строчных, слишком коротких/
  длинных кодах и кириллице, отказ на `minor_unit` вне диапазона.
- `test_money.py` — сложение/вычитание в одной валюте, `CurrencyMismatchError`
  при смешении валют, умножение на `Decimal`/`int` (в обе стороны через
  `__rmul__`) и отказ на `float`, деление на `Money`/`Decimal` возвращает
  `Decimal` и падает на `float`, округление `ROUND_HALF_UP` на граничных
  значениях `0.005 → 0.01`, `-0.005 → -0.01`, `2.675 → 2.68` из задания,
  `Money.zero`, отказ конструктора на `float`. Три приёма раздела 11.2:
  контрольные примеры (граничные значения округления), сверка с эталоном
  (`test_round_to_minor_unit_matches_manual_decimal_reference` сравнивает
  результат `Money` с прямым `Decimal.quantize(..., ROUND_HALF_UP)`,
  посчитанным в обход `Money`) и свойства через `hypothesis`
  (ассоциативность сложения, обратимость `a + b - b == a`, ноль как
  нейтральный элемент).
- `test_period.py` — `[start, end)`: левая граница входит, правая нет; отказ
  при `start >= end` (включая равенство и перестановку); `for_day`;
  `for_month` на обычном месяце, на декабре (переход через границу года на
  1 января следующего года) и на феврале — отдельно високосный 2024
  (29 дней) и невисокосный 2026 (28 дней, 29 февраля нет).
- `test_transaction.py` — положительный знак суммы (отказ на нуле и
  отрицательной сумме); соответствие `category_id`/`counter_account_id`
  виду операции (`income`/`expense` обязаны иметь категорию, `transfer`
  категорию запрещает и обязан иметь `counter_account_id != account_id`,
  `counter_account_id` вне `transfer` запрещён, `adjustment`/`interest`
  категорию не требуют); ограничение на будущий `occurred_at` для `posted`
  через `Transaction.new` (сутки — граница, `pending` без ограничения);
  сторно — исходная переходит `posted → reversed`, сторнирующая копирует
  поля движения денег, получает `reverses_id`, свой `id`/`created_at`,
  сразу `status = reversed` и `external_key = None`; повторное сторно и
  сторно не-`posted` операции (`pending`, уже `reversed`) дают
  `AlreadyReversedError`.
- `test_category.py` — регэксп слагов `^[a-z][a-z0-9_]*$` (валидные и
  невалидные слаги, включая кириллицу/иероглифы, дефис, ведущую цифру/
  подчёркивание); ограничение глубины `MAX_DEPTH = 2` — потомок третьего
  уровня (`depth = 2`) принимается, у него самого потомка уже нет;
  прямая сборка `Category` с `depth` вне диапазона, с рассинхроном
  `path`/`depth`, с `parent_id` у корня и без `parent_id` у некорневой —
  все отказывают; `new_child` наследует `kind` родителя;
  `build_default_categories` даёт 33 категории (27 расходных, 6 доходных),
  все с одним переданным `user_id`, все `path` уникальны, у каждого
  потомка родитель есть в наборе и того же `kind`, `sort_order` совпадает
  с порядком перечисления.
- `test_account.py` — валюта `opening_balance` обязана совпадать с валютой
  счёта: положительный случай (совпадение, включая нулевой остаток),
  отрицательный (`USD` остаток на счету в `RUB` → `InvariantViolationError`).
- `test_user.py` — положительный случай: значения по умолчанию из раздела
  3.3 (`base_currency = RUB`, `timezone = Europe/Moscow`, `locale = ru`,

**Решения и отложенное.**

- Пустой `.gitkeep` каталога `tests/unit/domain/` удалён — каталог больше
  не пуст, семь файлов тестов делают маркер лишним.
- Для `Money` использован единый `hypothesis`-параметр `_money_amounts`
  (`Decimal`, 4 знака после запятой, диапазон ±1 000 000) — достаточно для
  проверки алгебраических свойств и не выходит за точность `prec=28`
  контекста округления `Money`.
- Для `Transaction` инварианты собраны через локальную фабрику
  `_make_transaction` с сентинелом `_UNSET` для `category_id` — так каждый
  тест переопределяет ровно то поле, которое проверяет, без копирования
  двадцати позиционных аргументов сущности в каждый тест.
- Для `User` не нашлось рантайм-инварианта, эквивалентного Account'овскому
  `__post_init__`: класс — плоский `frozen`-датакласс без валидации. Вместо
  выдуманной проверки использована сама гарантия `frozen=True`
  (`FrozenInstanceError` при попытке присвоения) как отрицательный случай
  для документированного «неизменяем после создания» у `telegram_id`; это
  не дефект, а следствие того, что `User` — самая простая из сущностей
  этапа 1 и её инварианты (кроме умолчаний) описывают процесс на уровне
  выше сущности (ADR-009, уникальность в репозитории), а не сам класс.
