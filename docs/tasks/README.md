# Протокол задач для исполнителей

Каталог `docs/tasks/` — место, через которое главная сессия передаёт работу
субагентам-исполнителям и получает результат обратно. Каждая делегированная
задача существует как файл: сначала в нём лежит задание, потом к нему
дописывается результат.

Почему файл, а не только текст промпта. Промпт живёт ровно одну сессию: когда
она закрыта, ни задания, ни отчёта исполнителя не остаётся. Файл задачи
попадает в git, виден в истории и читается следующей сессией и следующим
исполнителем без расспросов. Кроме того, файл — единственный канал, по
которому исполнитель возвращает вопрос диспетчеру в письменном виде.

Правила, по которым главная сессия решает, звать исполнителя или работать
самой, описаны в `CLAUDE.md`, раздел «Делегирование».

## Имя файла

```text
docs/tasks/<YYYY-MM-DD>-<slug>.md
```

`<YYYY-MM-DD>` — дата заведения задачи. `<slug>` — короткое имя на английском
в kebab-case, по сути работы: `money-value-object`, `transactions-repository`,
`dashboard-screen`. Одна задача — один файл; подзадачи разных слоёв получают
разные файлы.

Файл задачи описывает работу, укладывающуюся примерно в семьдесят обращений
исполнителя к инструментам. Более крупная работа делится на два файла:
стоимость запуска растёт как квадрат числа обращений к модели, и один долгий
запуск обходится дороже двух коротких. Правило и измерение — в `CLAUDE.md`,
раздел «Делегирование», подраздел «Объём подзадачи».

## Обязательные поля задания

Задание заполняет главная сессия **до** запуска исполнителя. Пустых полей быть
не должно: поле, которое нечем заполнить, означает, что задача ещё не
декомпозирована.

- **Исполнитель** — ровно одна роль из `developer`, `tester`, `reviewer`,
  `analyst`, `designer`. Имя совпадает с именем файла в `.claude/agents/`.
- **Слой и раздел архитектуры** — какой слой из раздела 2.1
  `docs/architecture.md` затрагивается и на какой раздел документа опирается
  работа. Для задач вне продуктового кода — раздел, задающий правила. Номера
  разделов обязательны: исполнитель не должен искать их сам. Карта документа
  с номерами строк лежит в `docs/architecture-brief.md`, откуда исполнитель и
  начинает чтение.
- **Входные условия** — что уже готово к моменту запуска и какие файлы
  исполнитель обязан прочитать до первой правки.
- **Границы** — что исполнителю нельзя трогать в этой задаче: файлы, каталоги,
  сигнатуры, зависимости. Формулируются проверяемо: не «будь аккуратен», а
  «файлы в `src/finplan/domain/` не изменяются».
- **Критерий приёмки** — по чему видно, что работа закончена. Проверяемый:
  команда, которая проходит, файл, который существует и содержит названное,
  тест, который зелёный. Формулировка «сделать хорошо» критерием не является.

## Куда исполнитель пишет результат

В конец того же файла, разделом `## Результат исполнителя`. Раздел
дописывается; ничего выше него не переписывается и не удаляется — задание
должно остаться в том виде, в каком его получил исполнитель.

Внутри раздела:

1. **Сделано** — по сути изменения, а не списком файлов.
2. **Проверка** — какая команда запускалась и чем закончилась. Вывод
   упавшей команды приводится дословно, самой короткой решающей строкой.
   Пропущенная проверка называется пропущенной, с причиной.
3. **Решения и отложенное** — что выбрано и что осознанно не сделано.
4. **Вопросы диспетчеру** — пусто, если вопросов нет.

## Возврат вопроса вместо решения

Исполнитель, упершийся в архитектурное решение — выбор между двумя
допустимыми схемами, расхождение задания с `docs/architecture.md`, недостающее
в документе правило, — не принимает решение сам. Он пишет вопрос в раздел
«Вопросы диспетчеру», делает всё, что от этого решения не зависит, и
останавливается. Архитектурные решения принимает главная сессия.

## Журнал

`docs/dev-log.md` пополняет **только главная сессия**. Исполнители журнал не
правят: правило «одна задача — одна запись» из `CLAUDE.md` требует взгляда на
задачу целиком, а исполнитель видит только свою подзадачу.

## Архивация

Задача считается закрытой, когда её результат принят главной сессией и по ней
сделана запись в журнале. Закрытый файл переносится в `docs/tasks/done/` без
изменения содержимого; каталог заводится при первом переносе. В
`docs/tasks/` остаются только открытые задачи, поэтому список каталога — это
список незавершённой работы.

Исключение — файл плана этапа, `docs/tasks/<YYYY-MM-DD>-stage<N>-plan.md`. Он
заданием исполнителю не является: это список подзадач этапа с чекбоксами,
который ведёт главная сессия. Файл лежит в `docs/tasks/` до закрытия этапа, то
есть пока в нём остаются открытые подзадачи, и переносится в
`docs/tasks/done/` вместе с последней принятой подзадачей этапа.

## Шаблон файла задачи

```markdown
# <Название задачи одной строкой>

- **Исполнитель:** developer | tester | reviewer | analyst | designer
- **Слой:** domain | application | infrastructure | entrypoints | frontend | docs
- **Раздел архитектуры:** docs/architecture.md, раздел <N.M>
- **Заведена:** ГГГГ-ММ-ДД

## Входные условия

Что уже готово и какие файлы прочитать до первой правки.

## Задание

Что требуется сделать. Проза, без отсылок, непонятных вне сессии.

## Границы

- что нельзя трогать в этой задаче;
- каждая граница проверяема чтением диффа.

## Критерий приёмки

- проверяемое условие, по которому видно, что работа закончена.

## Результат исполнителя

_Заполняет исполнитель. Выше этой строки ничего не меняется._
```
