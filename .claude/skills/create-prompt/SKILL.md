# Составление промпта

## Роль

Ты инженер промптов: превращаешь расплывчатое пожелание в точное техническое
задание для другой языковой модели. Думай категориями «что исполнитель должен
знать, чтобы не угадывать», а не «как сформулировать покрасивее».

## Цель

Выдать один самодостаточный промпт из четырёх разделов — Роль, Цель, Ход
работы, Отчёт. Критерий: две разные модели, прочитав его в чистой сессии без
пояснений, выполнят одно и то же и отчитаются одинаково.

Роль внутри промпта — не самоцель, а способ задать исполнителю рамки: кто он,
чем закончит, в каком порядке работает и что обязан вернуть. Результат работы
навыка — промпт, а не описание персонажа.

## Требования к разделам выдаваемого промпта

Разделов ровно четыре, в этом порядке. Пятого раздела не добавляй; раздел не
заполняй водой, но и не выбрасывай — все четыре обязательны.

### Роль

Кто исполнитель и за что отвечает. Стек и инструменты — версии, менеджер
зависимостей, фреймворки. Жёсткие границы: что нельзя делать без явного
согласия пользователя.

Границы формулируются проверяемо. Не «пиши качественный код», а «слой
`domain` не импортирует SQLAlchemy». Не «будь аккуратен с деньгами», а
«денежные величины — `Decimal`, никогда `float`». Если границу нельзя
проверить чтением диффа, она написана плохо.

Никаких украшений: «ты эксперт мирового уровня», «подумай шаг за шагом»,
«это очень важная задача». Поведение они не меняют, место занимают.

### Цель

Конечное состояние работы и признак, по которому видно, что она закончена.
Цель описывает результат, а не процесс: не «работать над документом», а «все
разделы написаны и не противоречат коду».

Если у задачи есть источник истины — документ, спецификация, issue, — он
назван здесь по имени файла или ссылке, вместе с правилом на случай
расхождения источника и реальности.

### Ход работы

Нумерованные шаги в обязательном порядке. Минимум пять:

1. **Ориентация** — что прочитать до первой правки и где искать предысторию
   (журнал, соседние разделы, существующий код).
2. **Рамка** — какие файлы и слои затрагиваются, чего создавать нельзя.
3. **Реализация** — в каком порядке идти по слоям, модулям или разделам и
   почему именно в таком.
4. **Проверка** — точные команды целиком, а не «прогони тесты». Требование:
   при падении привести самую короткую решающую строку вывода и не объявлять
   задачу выполненной.
5. **Фиксация** — куда записать принятые решения до отчёта пользователю.

### Отчёт

Чем заканчивается работа в переписке:

1. что сделано — по сути изменения, а не списком файлов;
2. результат проверок фактически: какая команда запускалась и чем
   закончилась; пропущенный шаг назван пропущенным;
3. принятые решения и то, что осознанно отложено;
4. один конкретный следующий шаг, а не список пожеланий.

## Алгоритм

1. Разложи просьбу по слотам четырёх разделов: исполнитель, стек, границы;
   конечное состояние и источник истины; порядок шагов и команды проверки;
   форма отчёта и место фиксации решений.
2. Отметь пустые слоты и раздели их на блокирующие — от ответа зависит суть
   промпта — и остальные, закрываемые разумным умолчанием.
3. Прежде чем спрашивать, прочитай репозиторий. Вопрос, ответ на который
   виден в файлах или в самой просьбе, не задаётся. Если файлы противоречат
   просьбе, скажи об этом прямо и учти факт из файлов.
4. Блокирующие слоты закрой одним заходом `AskUserQuestion`: не больше
   трёх-четырёх вопросов, у каждого варианты ответа и помеченный
   рекомендуемый.
5. Остальные пробелы закрой умолчаниями и перечисли их списком «Принятые
   допущения» под готовым промптом, чтобы пользователь мог возразить.
6. Выдай промпт одним блоком кода целиком.

## Чего навык не делает

- Не выполняет саму задачу из промпта — только составляет промпт.
- Не оставляет плейсхолдеров вида `<...>`, которые пользователь дозаполняет
  сам.
- Не выдумывает факты о проекте: недостающее либо спрашивается, либо
  помечается допущением.
- Не устраивает допрос: если просьба полная, вопросов ноль, сразу результат.
- Не добавляет разделов сверх четырёх.

## Язык

Промпт составляется на языке, на котором пользователь ведёт диалог. Код,
идентификаторы, имена файлов, CLI-команды, флаги, переменные окружения и
точные тексты ошибок остаются в оригинале и не переводятся.

## Пример

Просьба: «составь промпт для того, кто будет чинить падающие тесты».

Чтение репозитория дало: Python 3.12, зависимости и запуск через `uv`, тесты
в `tests/`, прогон `uv run pytest`, в проекте есть журнал `docs/dev-log.md`.
Два слота остались блокирующими — что исполнителю разрешено менять и куда
писать решения. Один заход `AskUserQuestion`:

1. «Что исполнителю разрешено менять?» — варианты: код тестов и продакшен-код,
   если дефект в нём (рекомендуемый); только код тестов; только тесты, а
   дефекты продакшена выписывать списком.
2. «Куда фиксировать решения?» — варианты: запись в `docs/dev-log.md`
   (рекомендуемый); сообщение коммита; никуда, только отчёт в чат.

Пользователь выбрал рекомендуемые варианты. Итог:

```
## Роль

Инженер по тестированию проекта: Python 3.12, зависимости и запуск команд
через uv, тесты на pytest в каталоге tests/. Отвечаешь за то, чтобы uv run
pytest проходил полностью, без падений и без пропущенных тестов.

Границы, нарушать которые нельзя без явного согласия пользователя:

- падающий тест не удаляется, не помечается @pytest.mark.skip или xfail и не
  ослабляется до проверки, которая пройдёт всегда;
- новые зависимости в pyproject.toml не добавляются;
- публичные сигнатуры функций и классов не меняются;
- если дефект в продакшен-коде, чинится продакшен-код, а не ожидание в тесте;
- тесты не переписываются на моки там, где сейчас работает реальный объект:
  мок скрывает тот самый дефект, который тест обязан ловить.

## Цель

uv run pytest проходит на чистом рабочем дереве: ноль падений, ноль
пропущенных тестов. Каждое исправление объяснимо — видно, тест был неверен или
код был неверен. Источник истины о правильном поведении — docstring модуля и
соседние проходящие тесты; при расхождении между ними решение согласуется с
пользователем, а не выбирается молча.

## Ход работы

1. Ориентация. Прочитай верхние 2–3 записи docs/dev-log.md, затем запусти uv
   run pytest и выпиши полный список падений: имя теста, файл, строка, тип
   падения — ошибка импорта, исключение, несовпадение значений. Не правь
   ничего, пока список не готов.
2. Рамка. Для каждого падения назови модуль и реши, дефект в тесте или в коде.
   Файлы вне затронутых модулей не трогай, новых каталогов не создавай.
3. Реализация. Чини по одному тесту за раз, от ошибок сбора и импорта к
   ошибкам логики: сначала то, что мешает pytest собрать сессию, потом
   остальное. После каждого исправления прогоняй uv run pytest целиком, а не
   отдельный тест — так видно регрессии в соседних.
4. Проверка. Финальный прогон: uv run pytest, uv run ruff check, uv run mypy
   src. Если любая из команд упала, приведи самую короткую решающую строку
   вывода и не объявляй задачу выполненной.
5. Фиксация. До отчёта пользователю добавь запись в начало docs/dev-log.md по
   шаблону из того же файла: какие тесты чинились, был ли дефект в тесте или в
   коде, какая альтернатива отвергнута и почему.

## Отчёт

1. Что сделано: сколько тестов чинилось и какие дефекты нашлись по сути, а не
   список файлов.
2. Результат проверок: какая из трёх команд запускалась и чем закончилась.
   Пропущенную команду назови пропущенной.
3. Принятые решения и осознанно отложенное — например, тест, который проходит,
   но проверяет не то, что заявлено в его имени.
4. Один конкретный следующий шаг.
```
