# Перечень проверяемых правил для роли developer

- **Исполнитель:** analyst
- **Слой:** docs
- **Раздел архитектуры:** docs/architecture.md, разделы 1–5
- **Заведена:** 2026-09-21

## Входные условия

В репозитории продуктового кода пока нет: есть `docs/architecture.md` со всеми
четырнадцатью разделами, `CLAUDE.md` с ролью главной сессии и файлы агентов в
`.claude/agents/`. Роль `developer` описана в `.claude/agents/developer.md`;
часть правил уже перечислена там в разделе «Роль», и задача — проверить этот
перечень против документа.

Прочитать до первой правки: `docs/architecture.md`, разделы 1–5 целиком;
`docs/tasks/README.md` — формат результата; `.claude/agents/developer.md` —
текущий перечень правил.

## Задание

Выписать из разделов 1–5 `docs/architecture.md` перечень проверяемых правил,
которые обязан соблюдать исполнитель роли `developer` при написании
продуктового кода. Правило считается проверяемым, если его нарушение видно
при чтении диффа или по выводу команды.

Каждый пункт перечня оформить тремя частями: формулировка правила; ссылка на
раздел документа, откуда оно взято; признак нарушения — что именно в коде
означает, что правило нарушено.

Отдельным списком назвать те пункты перечня, которых сейчас нет в разделе
«Роль» файла `.claude/agents/developer.md`, — они кандидаты на добавление
туда. Сам файл агента не править.

## Границы

- правится только этот файл задачи; `.claude/agents/developer.md`,

## Результат исполнителя

### Перечень проверяемых правил из разделов 1–5

#### Слой domain

1. **`domain` не импортирует ничего из `application`, `infrastructure` или `entrypoints`.**
   - Раздел: 2.2 «Правила слоёв»
   - Признак нарушения: в импортах файлов `src/finplan/domain/**/*.py` обнаружены строки `from finplan.application`, `from finplan.infrastructure` или `from finplan.entrypoints`.

2. **`domain` не импортирует SQLAlchemy, aiogram или FastAPI.**
   - Раздел: 2.2 «Правила слоёв»
   - Признак нарушения: в импортах файлов `src/finplan/domain/**/*.py` обнаружены `sqlalchemy`, `aiogram` или `fastapi`.

3. **Денежные величины представляются как value object `Money(amount: Decimal, currency: Currency)`, никогда не как `float`.**
   - Раздел: 3.1 «Представление денег»
   - Признак нарушения: в коде встречаются денежные суммы типа `float` или арифметика прямо над суммами без оборачивания в `Money`.

4. **В базе данные денежные значения хранятся как `numeric(20, 4)`, то есть 20 знаков всего, 4 после запятой.**
   - Раздел: 3.1 «Представление денег», 4.1 «Общие соглашения»
   - Признак нарушения: в миграции или ORM-модели столбцы денежных сумм определены с иной точностью (например, `NUMERIC(19, 2)`).

5. **Политика округления денежных сумм: `ROUND_HALF_UP` до минорной единицы валюты; это задаётся явно в контексте `decimal.Context` в `domain/common/money.py`.**
   - Раздел: 3.1 «Представление денег»
   - Признак нарушения: округление использует другой режим (например, `ROUND_HALF_EVEN`), либо в коде видны вызовы `round()` на `float` вместо `Money`.

6. **Период представляется как value object `Period` с полуинтервалом `[from, to)`: день открытия входит, день закрытия входит в следующий период.**
   - Раздел: 5.1 «Соглашения о подсчёте дней»
   - Признак нарушения: в коде встречаются вычисления дней между датами как обычное вычитание без учёта полуинтервала, или используется замкнутый интервал `[from, to]`.

#### Слой application

7. **Один use case — один класс с методом `__call__`, принимающий DTO на входе и возвращающий DTO на выходе.**
   - Раздел: 2.2 «Правила слоёв»
   - Признак нарушения: use case содержит несколько публичных методов (кроме `__init__`), либо в методе `__call__` явно открывается транзакция вместо использования Unit of Work.

8. **Транзакция открывается на уровне use case через Unit of Work, не в слое `infrastructure` и не в точке входа.**
   - Раздел: 2.2 «Правила слоёв»
   - Признак нарушения: в файле `entrypoints/**/*.py` или `infrastructure/**/*.py` обнаружены прямые вызовы `session.begin()`, `session.commit()` или контекстный менеджер `async with session.begin()`.

#### Слой infrastructure

9. **`application` зависит только от `domain` и своих `ports`; реализации портов подставляются в `container.py`.**
   - Раздел: 2.2 «Правила слоёв»
   - Признак нарушения: в файле `src/finplan/application/**/*.py` импортируются конкретные реализации из `infrastructure` (например, `from finplan.infrastructure.db.repositories import ...`).

10. **Таблицы `transactions`, `account_valuations`, `exchange_rates`, `notification_log` являются неизменяемыми журналами: добавление новых записей разрешено, редактирование и удаление — запрещены на уровне БД (триггер).**
    - Раздел: 4.2 «Неизменяемый журнал против пересчитываемых данных»
    - Признак нарушения: в миграции отсутствует триггер `trg_transactions_immutable` или аналогичные для `account_valuations`, либо его логика позволяет `UPDATE` любых полей, кроме `status`.

11. **Любой кэш (например, в таблицах `balance_snapshots`, `deposit_metrics`) обязан быть восстановим из журнальных таблиц командой `finplan recalc --from <date>`.**
    - Раздел: 4.2 «Неизменяемый журнал против пересчитываемых данных»
    - Признак нарушения: кэш-таблица заполняется данными, которые нельзя пересчитать из журнала, либо отсутствует команда восстановления кэша.

12. **Первичные ключи в таблицах (кроме справочника валют) — `uuid`, генерируемые приложением как UUIDv7 для монотонности.**
    - Раздел: 4.1 «Общие соглашения»
    - Признак нарушения: первичный ключ в таблице задан как `SERIAL`, `BIGINT` или иной тип, либо оставлен дефолтный `uuid` без явного указания, что приложение генерирует UUIDv7.

13. **Все временные метки в базе — `timestamptz`, хранятся в UTC.**
    - Раздел: 4.1 «Общие соглашения»
    - Признак нарушения: в схеме встречаются временные метки типа `timestamp` без часового пояса или `datetime`.

14. **Календарные даты, привязанные к локали пользователя (например, `occurred_on`, `valuated_on`), должны быть типа `date`.**
    - Раздел: 4.1 «Общие соглашения»
    - Признак нарушения: дата хранится как `timestamp` или `timestamptz` в таблице `transactions`, `account_valuations`.

15. **Перечисления в БД реализуются как `text` с ограничением `CHECK (col IN (...))`, не как нативный `ENUM`.**
    - Раздел: 4.1 «Общие соглашения»
    - Признак нарушения: в миграции используется команда `CREATE TYPE ... AS ENUM` или в ORM определено поле как `enum.Enum`.

16. **Имена ограничений (constraint) задаются по соглашению SQLAlchemy: `pk_%(table_name)s`, `fk_%(table_name)s_%(column_0_name)s`, `uq_...`, `ck_...`, `ix_...`.**
    - Раздел: 4.1 «Общие соглашения»
    - Признак нарушения: в миграции встречаются constraint с неправильными именами (например, `pk_id` вместо `pk_transactions`) или без имён.

17. **Таблица `transactions` имеет триггер, который разрешает изменять только поле `status` (переход `posted → reversed`) и запрещает удаление.**
    - Раздел: 4.3 «Таблицы» → `transactions`
    - Признак нарушения: триггер `trg_transactions_immutable` отсутствует или позволяет редактировать иные поля.

#### Слой entrypoints

18. **`entrypoints` не содержат бизнес-логики: разбор входа, вызов use case, форматирование ответа.**
    - Раздел: 2.2 «Правила слоёв»
    - Признак нарушения: в файле `entrypoints/**/*.py` обнаружена ветвление по доменным правилам, условия на значения денежных сумм или валюты, пересчёты на дату.

#### Row Level Security

19. **PostgreSQL Row Level Security включена на всех пользовательских таблицах (во всех, где есть `user_id`); политика проверяет `user_id = current_setting('app.user_id')`.**
    - Раздел: 4.5 «Изоляция данных на уровне БД»
    - Признак нарушения: в миграции отсутствует `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` или `CREATE POLICY` для таблицы, либо политика проверяет не `current_setting`.

20. **В начале каждой транзакции приложение выполняет `SET LOCAL app.user_id = :user_id`, что делает `SqlAlchemyUnitOfWork` автоматически.**
    - Раздел: 4.5 «Изоляция данных на уровне БД»
    - Признак нарушения: команда `SET LOCAL` отсутствует в `infrastructure/db/uow.py` при открытии сессии, или передача `app.user_id` забыта.

### Кандидаты на добавление в `.claude/agents/developer.md`

Из перечня выше в разделе «Роль» файла `developer.md` сейчас отсутствуют следующие правила (номера из перечня выше):

- **4** — точность денежных значений `numeric(20, 4)` в БД
- **5** — явная политика округления `ROUND_HALF_UP`
- **8** — транзакция открывается на уровне use case через Unit of Work
- **9** — реализации портов подставляются в `container.py`
- **10** — неизменяемость таблиц `transactions`, `account_valuations` на уровне БД (триггер)
- **11** — кэш должен быть восстановим из журнала
- **12** — первичные ключи — UUIDv7, генерируемые приложением
- **13** — все временные метки — `timestamptz` в UTC
- **14** — календарные даты — тип `date`
- **15** — перечисления как `text + CHECK`, не ENUM
- **16** — соглашение об именах constraint
- **17** — триггер на `transactions` разрешает только `status`, запрещает удаление
- **18** — `entrypoints` не содержат бизнес-логики (есть общая формулировка, но можно уточнить)
- **19** — Row Level Security на всех пользовательских таблицах
- **20** — `SET LOCAL app.user_id` в Unit of Work при открытии сессии

Остальные пункты (1, 2, 3, 6, 7) уже упоминаются в разделе «Роль» `developer.md`, хотя формулировка может отличаться.
