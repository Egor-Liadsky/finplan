## Задание

1. **`account_movements`.** Сумма движений по каждому счёту в валюте
   счёта: доход прибавляется, расход и перевод вычитаются, учитываются
   только `posted`; сторнированная операция вместе со своей сторнирующей
   записью в сумме не отражается. Суммы сравниваются как `Decimal`
   точно, без округления и без `float`.

2. **`totals_by_category`.** Суммы `base_amount` по категориям за
   период: операция ровно в момент `start` входит, ровно в момент `end`
   не входит (полуинтервал `[from, to)`); операции без категории, не
   `posted` и других видов не учитываются; доходы и расходы разделены.

3. **Изоляция, раздел 11.4.** Параметризованный тест, который перебирает
   все публичные методы четырёх репозиториев и `SqlAlchemyLedgerQueries`,
   получая список методов автоматически (например, через `inspect` по
   классу, без приватных методов), и требует, чтобы под Unit of Work
   пользователя B данные пользователя A не возвращались: `get` даёт
   `None`, `list` и агрегаты не содержат объектов A, а `mark_reversed` с
   чужим идентификатором не меняет операцию A. Метод, для которого
   способ проверки не описан в таблице теста, должен ронять тест, а не
   пропускаться молча, — иначе новый метод можно добавить без проверки
   изоляции. Отдельно проверить, что без явного фильтра по `user_id`
   чужие строки отсекает сама RLS: прямой `SELECT` из `transactions` под
   `finplan_app` с `app.user_id` пользователя B не возвращает строк A.

Все тесты помечаются `pytestmark = pytest.mark.integration`.

## Результат исполнителя

**Сделано.** Добавлены два файла тестов в `tests/integration/repositories/`,
оба используют фикстуры `uow_factory`/`app_connection` из первой части
подзадачи без изменений — 22 новых теста, все помечены `pytestmark =
pytest.mark.integration`.

`test_ledger_queries.py` (6 тестов):
- `TestAccountMovements` — контрольный пример на `Decimal` (доход
  `500.1234`, расход `120.5000`, перевод `50.0000` между двумя счетами
  одного пользователя → `329.6234` на счёте-источнике, `50.0000` на
  счёте-получателе, сравнение точное, без округления); отдельный тест на
  то, что счёт без единой `posted`-операции не попадает в словарь вовсе
  (операция в статусе `pending` игнорируется); отдельный тест на пару
  «исходная запись + сторно» — обе строки после `Transaction.reverse()` +
  `mark_reversed()` + `add(reversal)` получают `status = reversed` (форма
  сторно раздела 3.3) и обе исключаются запросом, а не взаимно
  компенсируют друг друга нулём.
- `TestTotalsByCategory` — тест на полуинтервал `[start, end)`: операция
  ровно в `start` входит, операция ровно в `end` (следующий месяц) не
  входит; тест на исключение операции без категории (перевод),
  не-`posted` (`pending`) и категории без операций; тест на раздельные
  суммы `income`/`expense` по одной и той же категории каждого вида с
  несколькими операциями.

`test_tenant_isolation.py` (16 тестов: 15 параметризованных + 1 обычный):
- Список методов собирается автоматически через `vars(cls)` +
  `inspect.iscoroutinefunction` по пяти классам (`SqlAlchemyUserRepository`,
  `SqlAlchemyAccountRepository`, `SqlAlchemyCategoryRepository`,
  `SqlAlchemyTransactionRepository`, `SqlAlchemyLedgerQueries`) — итого 15
  публичных методов (3+3+3+4+2). Для каждого — запись в словаре `CHECKS`
  с конкретной проверкой; метод без записи не пропускается, а роняет
  параметризованный кейс через `pytest.fail` с сообщением, называющим
  метод. Продемонстрировано (пункт критерия приёмки): временно добавлена
  строка `ALL_METHODS.append(("transactions",
  "temp_stub_method_without_checker"))`, прогнан
  `uv run pytest tests/integration/repositories/test_tenant_isolation.py -k
  temp_stub_method -q` → `1 failed`, `Failed: нет описанной проверки
  изоляции для transactions.temp_stub_method_without_checker: ...`; строка
  затем убрана, `git diff` по файлу после уборки пуст относительно
  финальной версии.
- Проверки для `get`/`list`/агрегатов — то, что описано в задании:
  `get` даёт `None`, `list`/`account_movements`/`totals_by_category` не
  содержат объектов владельца. `mark_reversed` с `user_id` соседа не
  находит строку владельца (`WHERE user_id = ...` не совпадает) и не
  меняет её статус — проверено повторным чтением через `UnitOfWork`
  владельца. `last_reversible` соседа с тем же `source` возвращает `None`.
- Для методов записи (`users.add`, `accounts.add`, `categories.add_many`,
  `transactions.add`) проверка расширена за пределы явного текста задания
  (которое перечисляет только `get`/`list`/`mark_reversed`): сосед B
  пытается вставить домен-объект с `user_id = owner.id` — политика RLS
  `p_*_owner` (`USING (user_id = app.user_id)` без отдельного `WITH
  CHECK` — PostgreSQL по умолчанию переиспользует `USING` и для новых
  строк) отклоняет вставку кодом `42501`
  (`insufficient_privilege`/`InsufficientPrivilegeError`), что отличимо от
  `DuplicateError` (`23505`), которую ловит сам репозиторий. Это решение
  зафиксировано явно (не входило в дословный список задания), потому что
  без него `add`/`add_many` не попали бы ни в один описанный кейс и,
  по правилу задания, должны были бы ронять тест как «метод без
  проверки» — а он есть и как минимум так же важен для 11.4, как
  проверка чтения: без него оставался бы непроверенным путь «сосед
  создаёт строку от чужого имени».
- `users.get_by_telegram_id` — единственный метод, который **намеренно**
  не проверяет изоляцию по `UnitOfWork`: по разделу 4.5 он идёт через
  `SECURITY DEFINER`-функцию `find_user_by_telegram_id`, обходящую
  `app.user_id`, потому что вызывается до того, как пользователь
  аутентифицирован и известен его `id`. Проверка для него в `CHECKS`
  есть и документирует это исключение прямо в докстринге функции-чекера
  вместо того, чтобы просто не описывать метод: под `UnitOfWork` соседа
  он всё равно находит и возвращает владельца, и это ожидаемое, а не
  ошибочное поведение.
- Отдельный класс `TestRowLevelSecurityDirectSelect` — прямой `SELECT id
  FROM transactions` без `WHERE user_id = ...` под `finplan_app` с
  `app.user_id` соседа не возвращает строку владельца, и контрольная
  часть того же теста показывает, что под `app.user_id` владельца та же
  строка тем же запросом видна — значит «не видно» в первой части
  объясняется именно RLS-политикой, а не тем, что данных физически ещё
  нет (тот же аргумент, что в докстринге `conftest.py` первой части).

**Решения и отложенное.**
- Проверки изоляции для методов записи (`add`/`add_many`) через RLS-код
  `42501` — решение, принятое по месту (см. выше), а не архитектурное:
  оно не меняет и не обходит продуктовый код, только использует уже
  существующее поведение миграции. Вопросов диспетчеру по этому поводу
  нет, но решение явно названо, так как оно расширяет буквальный текст
  задания («get даёт None, list и агрегаты не содержат объектов A, а
  mark_reversed... не меняет операцию A» не упоминает `add`).
- `test_tenant_isolation.py` использует собственную фикстуру `world`
  (а не переиспользует `_setup_owner` из `test_transactions.py` или
  `test_ledger_queries.py`), потому что ей нужны также «недоставленные»
  hostile-объекты для проверки методов записи — общий helper усложнил бы
  сигнатуру ради двух мест использования, и `docs/tasks/README.md`/задание
  не требуют консолидации хелперов между файлами тестов.
- Дефектов продуктового кода не найдено: `account_movements` и
  `totals_by_category` в `src/finplan/infrastructure/db/queries/ledger.py`
  ведут себя точно так, как описывает докстринг порта `LedgerQueries`
  (раздел 2.2), включая исключение сторно-пар — это следствие того, что
  и исходная, и сторнирующая запись получают `status = reversed`, а не
  отдельной логики в самом SQL-запросе; RLS-политики `migrations/
  versions/20260924_1600-d6cb2637f739_grant_privileges_and_rls.py`
  блокируют кросс-tenant `INSERT` так же, как и `SELECT`.
- Порядок элементов в `list`-проверках (`accounts.list`,
  `categories.list`) не важен для isolation-проверки и не проверяется
  здесь отдельно — это уже покрыто раундтрип-тестами первой части.
