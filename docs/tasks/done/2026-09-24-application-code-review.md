**Проверка.**

Блокирующие («нарушение»):

- `src/finplan/application/use_cases/transactions/record_transaction.py:78`
  и `:83` — сумма операции создаётся как
  `Money(command.amount, account.currency)` и `base_amount=command.amount`
  без вызова `Money.round_to_minor_unit()`. Нарушает раздел 3.1, таблицу
  округления, строку «Хранение операции, введённой пользователем |
  `ROUND_HALF_UP` до `minor_unit` валюты» — метод объявлен в
  `domain/common/money.py` и, по тому же разделу, «используется явно», а
  здесь не вызван вовсе. Последствие: сумма с точностью выше `minor_unit`
  валюты (например, `10.567` для RUB, где `minor_unit = 2`, или любая
  дробная сумма для JPY с `minor_unit = 0`) уходит в `Transaction`
  нетронутой; `NUMERIC(20, 4)` в БД её не отбросит, поэтому в журнал попадёт
  сумма, не соответствующая политике округления, с расхождением при сверке
  с выпиской банка, для которой эта политика и выбиралась (3.1, абзац
  «Округление»).

- `src/finplan/application/use_cases/auth/register_user.py:48` — исправление
  таймзоны из «Известного и уже учтённого» ложится сюда: `ZoneInfo(command.
  timezone)` создаётся без перехвата `ZoneInfoNotFoundError`. Место — use
  case, а не DTO: раздел 2.2 относит «команда противоречит данным» к
  `InvalidCommandError` из `application/errors.py`, а не к валидации
  pydantic, и `RegisterUserCommand` в `dto/auth.py` не место для бизнес-
  проверки существования IANA-таймзоны. Уровень выше уже записанного:
  сейчас `ZoneInfoNotFoundError` не наследует `ApplicationError` и не
  является `DomainError` (это стандартное исключение `zoneinfo`), поэтому
  оно не подпадает ни под одну из двух ветвей, которые раздел 2.2 явно
  называет способом сообщить об отказе сценария, и `entrypoints` не смогут
  обработать его тем же путём, что `ApplicationError`/`DomainError`.
  Прогон теста с `xfail(strict=True)` не выполнялся — это подтверждает
  `tester`.

Замечания (риск на следующих подзадачах этапа 1):

- `src/finplan/application/use_cases/auth/register_user.py:44-45` —
  `async with self._uow_factory(new_id) as uow:` открывает транзакцию
  свежим `uuid4()`, а не `None`, и в ней же выполняется
  `uow.users.get_by_telegram_id(...)` — это ровно случай «поиск пользователя
  по `telegram_id`, пока его `id` неизвестен» из раздела 2.2, для которого
  контракт разрешает `None`. Текущий код опирается на то, что при
  существующем пользователе `uow.users.add(user)` ниже упадёт
  `DuplicateError`, и тогда код переоткрывает `UnitOfWork` уже с `None`
  (строка 84) и находит пользователя корректно — по факту сценарий не
  ломается. Риск проявится на подзадаче 8 (`infrastructure`, RLS по 4.5):
  если `SqlAlchemyUnitOfWork` выставит `app.user_id = new_id` и RLS-политика
  на `users` фильтрует по `id`, первый `get_by_telegram_id` на строке 45
  всегда будет видеть только ещё не существующую строку и всегда провалится
  в ветку `DuplicateError` — не баг, но лишний `INSERT`, обречённый на
  конфликт, при каждой регистрации уже существующего пользователя.

- `src/finplan/application/use_cases/transactions/record_transaction.py:77`
  — `status=TransactionStatus.POSTED` передаётся безусловно, независимо от
  `occurred_at`. Раздел 3.3, инварианты `Transaction`: «`occurred_at` не
  может быть более чем на 1 день в будущем для `status = posted`; будущие
  операции создаются со `status = pending`» — сценарий создания `pending`
  здесь не реализован вовсе. При `occurred_at` дальше суток в будущем
  `Transaction.new` (уже существующий код, раздел 3.3) поднимет
  `InvariantViolationError`, которая по правилу 2.2 уйдёт наверх как
  `DomainError` без обёртки — это не противоречит контракту передачи
  ошибки, но противоречит документированному поведению: операция должна
  быть создана как `pending`, а не отвергнута. Риск проявится на подзадаче
  8-9b: `TransactionRepository` в `ports/repositories.py` не имеет метода
  для перевода `pending → posted` (только `mark_reversed`), то есть даже
  после исправления use case порт придётся расширять — стоит учесть при
  проектировании протокола заранее, а не по факту реализации бота.
